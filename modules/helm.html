Helm — The Package Manager for Kubernetes

Why Helm Exists

Deploying an app to Kubernetes means writing YAML — lots of it. A production app typically needs a Deployment, a Service, a ConfigMap, a Secret, an Ingress, HorizontalPodAutoscaler, and more. That's 5-10 YAML files just for one app. Now imagine deploying that app to dev, staging, and production with slightly different values in each environment.

Without Helm you copy-paste YAML files and manually edit them for each environment. When something changes — a new image tag, a port number — you edit multiple files and hope you got them all. That's error-prone and doesn't scale.

📦 Analogy — apt / npm for Kubernetes

Think of Helm the same way you think of apt install nginx on Ubuntu or npm install express in Node.js. Instead of manually downloading binaries and configuring them, you run one command and get a working, production-grade installation. Helm does the same thing for Kubernetes applications.

Core Concepts

📋
Chart
A Helm package. Contains all the Kubernetes YAML templates for an application, along with default configuration values.
🚀
Release
A running instance of a chart in your cluster. You can install the same chart multiple times — each is a separate release with its own name.
⚙️
Values
Configuration that gets injected into chart templates. Override defaults per environment (dev vs prod) without touching the templates.
🗄️
Repository
A collection of charts, hosted online. Like Docker Hub for images — but for Helm charts. Artifact Hub is the main public registry.

Chart File Structure

When you run helm create my-app, Helm scaffolds this structure:

my-app/ ├── Chart.yaml # Chart metadata — name, version, description ├── values.yaml # Default configuration values ├── charts/ # Dependency charts (sub-charts) └── templates/ # Kubernetes YAML templates ├── deployment.yaml ├── service.yaml ├── ingress.yaml ├── configmap.yaml ├── _helpers.tpl # Reusable template snippets └── NOTES.txt # Post-install instructions shown to user
Chart.yaml
apiVersion: v2 name: my-app description: A Helm chart for my Node.js application type: application version: 0.1.0 # Chart version (you bump this on changes) appVersion: "1.0.0" # App version (the Docker image tag)

values.yaml — The Heart of Helm

This is where all your configurable values live. Templates reference these with {{ .Values.key }}.

values.yaml
replicaCount: 2 image: repository: myregistry/my-app tag: "1.0.0" pullPolicy: IfNotPresent service: type: ClusterIP port: 80 targetPort: 3000 ingress: enabled: true host: app.example.com resources: requests: cpu: "100m" memory: "128Mi" limits: cpu: "500m" memory: "256Mi" env: NODE_ENV: production LOG_LEVEL: info
💡 Per-environment overrides

Keep a values.yaml for defaults, then values-dev.yaml, values-staging.yaml, values-prod.yaml for overrides. Pass them with -f values-prod.yaml at install time. Only put the things that differ — Helm merges them.

Templates — YAML + Go Templating

Templates are regular Kubernetes YAML files with {{ }} placeholders that Helm fills in from values.yaml.

templates/deployment.yaml
apiVersion: apps/v1 kind: Deployment metadata: name: {{ .Release.Name }}-app # e.g. "myrelease-app" labels: app: {{ .Chart.Name }} version: {{ .Chart.AppVersion }} spec: replicas: {{ .Values.replicaCount }} selector: matchLabels: app: {{ .Chart.Name }} template: spec: containers: - name: {{ .Chart.Name }} image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}" imagePullPolicy: {{ .Values.image.pullPolicy }} ports: - containerPort: {{ .Values.service.targetPort }} env: {{- range $key, $val := .Values.env }} - name: {{ $key }} value: {{ $val | quote }} {{- end }} resources: {{- toYaml .Values.resources | nindent 12 }}

Essential Helm Commands

Terminal — Core Workflow
# ── Repositories ────────────────────────────────── helm repo add bitnami https://charts.bitnami.com/bitnami helm repo update helm search repo bitnami/nginx helm search hub wordpress # search Artifact Hub # ── Install ──────────────────────────────────────── helm install my-nginx bitnami/nginx helm install my-app ./my-app # local chart helm install my-app ./my-app -f values-prod.yaml # with overrides helm install my-app ./my-app --set image.tag=2.0.0 # ── View ────────────────────────────────────────── helm list # all releases helm status my-app # release status helm get values my-app # values used helm get manifest my-app # rendered YAML # ── Upgrade ─────────────────────────────────────── helm upgrade my-app ./my-app --set image.tag=2.1.0 helm upgrade --install my-app ./my-app # install if not exists # ── Rollback ────────────────────────────────────── helm history my-app # see revision history helm rollback my-app 1 # roll back to revision 1 # ── Debug ───────────────────────────────────────── helm template my-app ./my-app # render templates locally helm lint ./my-app # validate chart helm install my-app ./my-app --dry-run # simulate install # ── Uninstall ───────────────────────────────────── helm uninstall my-app

Real-World Example — Deploying PostgreSQL

Without Helm: write a Deployment, StatefulSet, Service, PVC, Secret, ConfigMap — hundreds of lines. With Helm:

Terminal
helm repo add bitnami https://charts.bitnami.com/bitnami helm repo update helm install my-postgres bitnami/postgresql \ --set auth.postgresPassword=secret123 \ --set primary.persistence.size=20Gi \ --set replication.enabled=true \ --set replication.numSynchronousReplicas=1 NAME: my-postgres LAST DEPLOYED: Mon Jan 15 09:23:11 2024 STATUS: deployed NOTES: PostgreSQL can be accessed via port 5432 on the following DNS name: my-postgres-postgresql.default.svc.cluster.local

That single command deployed a production-grade PostgreSQL with replication, persistent storage, secrets management, and health checks — all from a battle-tested chart maintained by the Bitnami team.

→
Docker build
→
Push image

→
Deployed ✓
Jenkinsfile / GitHub Actions step
# Build and push image docker build -t myregistry/my-app:$GIT_SHA . docker push myregistry/my-app:$GIT_SHA # Deploy with Helm — upgrades if exists, installs if new helm upgrade --install my-app ./helm/my-app \ --namespace production \ --create-namespace \ --set image.tag=$GIT_SHA \ -f helm/my-app/values-prod.yaml \ --wait \ --timeout 5m
💡 --wait flag

--wait tells Helm to block until all pods are Running and Ready. Your pipeline fails fast if the deployment is broken — rather than succeeding and leaving broken pods behind.

🚀 Mini Project — Chart Your Own App

Take the Docker app from Module 09 and package it as a Helm chart:

  1. 1Run helm create my-node-app and explore the generated structure
  2. 2Edit values.yaml — set your image repository and tag
  3. 3Run helm template my-node-app ./my-node-app to see the rendered YAML
  4. 4Run helm lint ./my-node-app to validate
  5. 5Install to Minikube: helm install my-node-app ./my-node-app
  6. 6Upgrade with a new tag: helm upgrade my-node-app ./my-node-app --set image.tag=2.0.0
  7. 7Roll back: helm rollback my-node-app 1
✅ Module Summary
  • Helm is the package manager for Kubernetes — it templates your YAML and manages releases
  • A Chart is the package, a Release is a running instance, Values are the config
  • values.yaml holds defaults; override per environment with -f values-prod.yaml
  • helm upgrade --install is the standard CI/CD deploy command — idempotent and safe
  • helm rollback gives instant recovery; helm history shows what changed and when
  • Use helm template and helm lint locally before deploying
