Nginx — Reverse Proxy, Load Balancer & Web Server

What Nginx Actually Does

Nginx (pronounced "engine-x") is the most widely deployed web server in the world. But calling it just a "web server" undersells it. In DevOps, you use Nginx primarily as a reverse proxy and load balancer — the traffic cop that sits in front of all your backend services.

🏨 Analogy — Hotel Receptionist

Imagine a hotel with 10 floors of rooms (your backend services). Guests (HTTP requests) don't wander the building looking for their room. They go to the receptionist (Nginx) who checks their request and directs them: "Room 301 is Node.js on port 3000, Room 405 is the Python API on port 5000, the conference room is the static website." The guest never knows what's behind the desk. That's a reverse proxy.

Installing & Basic Config

Terminal — Install
# Ubuntu / Debian sudo apt update && sudo apt install nginx -y sudo systemctl start nginx sudo systemctl enable nginx # start on boot sudo systemctl status nginx # Test config before reloading (always do this!) sudo nginx -t nginx: the configuration file /etc/nginx/nginx.conf syntax is ok nginx: configuration file /etc/nginx/nginx.conf test is successful # Reload config without downtime sudo nginx -s reload

Nginx config lives in /etc/nginx/. The key files:

/etc/nginx/ ├── nginx.conf # Main config — worker processes, logging ├── sites-available/ # Config files for each site (disabled) │ └── myapp.conf ├── sites-enabled/ # Symlinks to active sites │ └── myapp.conf → ../sites-available/myapp.conf └── conf.d/ # Alternative — drop .conf files here

Reverse Proxy — The Most Common Pattern

Your Node.js app runs on port 3000 internally. Nginx listens on port 80/443 and forwards traffic to it. Users only ever talk to Nginx.

/etc/nginx/sites-available/myapp.conf
server { listen 80; server_name app.example.com; # Redirect HTTP → HTTPS return 301 https://$host$request_uri; } server { listen 443 ssl; server_name app.example.com; # SSL certificates (from Let's Encrypt) ssl_certificate /etc/letsencrypt/live/app.example.com/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem; # Reverse proxy to your Node.js app location / { proxy_pass http://localhost:3000; proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection 'upgrade'; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_cache_bypass $http_upgrade; } # Serve static files directly (faster than Node.js) location /static/ { root /var/www/myapp; expires 30d; add_header Cache-Control "public, immutable"; } }
Terminal — Enable site
sudo ln -s /etc/nginx/sites-available/myapp.conf /etc/nginx/sites-enabled/ sudo nginx -t && sudo nginx -s reload

Load Balancing

Running multiple instances of your app for redundancy and scale? Nginx distributes traffic across them.

nginx.conf — Load Balancer
# Define the pool of backend servers upstream myapp_servers { # Round-robin by default — each request goes to next server server 10.0.0.1:3000; server 10.0.0.2:3000; server 10.0.0.3:3000; # Or: least_conn — send to server with fewest active connections # least_conn; # Or: ip_hash — same client always hits same server (session sticky) # ip_hash; # Weight — server 1 gets 3x more traffic # server 10.0.0.1:3000 weight=3; # server 10.0.0.2:3000 weight=1; # Health check — mark server down after 3 failures server 10.0.0.1:3000 max_fails=3 fail_timeout=30s; server 10.0.0.2:3000 max_fails=3 fail_timeout=30s; # Hot standby — only used if all others are down server 10.0.0.4:3000 backup; } server { listen 80; location / { proxy_pass http://myapp_servers; } }

Rate Limiting

Protect your API from abuse and DDoS attacks by limiting how many requests a client can make.

nginx.conf — Rate Limiting
# Define a rate limit zone — 10 req/sec per IP, 10MB memory limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s; server { location /api/ { # Apply limit — allow burst of 20 before rejecting limit_req zone=api_limit burst=20 nodelay; limit_req_status 429; proxy_pass http://localhost:3000; } # Stricter limit for login endpoint location /api/auth/login { limit_req zone=api_limit burst=5 nodelay; proxy_pass http://localhost:3000; } }

Nginx in Docker (Real-World Pattern)

In containerised environments, Nginx runs as a sidecar or as the entry-point container in a Docker Compose stack.

docker-compose.yml
version: '3.8' services: nginx: image: nginx:alpine ports: - "80:80" - "443:443" volumes: - ./nginx.conf:/etc/nginx/conf.d/default.conf - ./certs:/etc/nginx/certs depends_on: - api - frontend api: build: ./api expose: - "3000" # only accessible to nginx, not the host frontend: build: ./frontend expose: - "8080"
nginx.conf (for Docker Compose)
upstream api { server api:3000; } # Docker service name = hostname upstream frontend { server frontend:8080; } server { listen 80; location /api/ { proxy_pass http://api; } location / { proxy_pass http://frontend; } }

✅ Module Summary
  • Nginx acts as a reverse proxy — clients talk to Nginx, not your backends directly
  • Load balancing strategies: round-robin (default), least_conn, ip_hash, weighted
  • Always run nginx -t before reloading — catches config errors without downtime
  • nginx -s reload reloads config with zero dropped connections
  • In Docker, use service names (e.g. proxy_pass http://api) — Docker DNS resolves them
  • Rate limiting with limit_req_zone protects APIs from abuse and DDoS
  • Always redirect HTTP → HTTPS with return 301 in the port 80 block
