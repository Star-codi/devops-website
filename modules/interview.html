Interview Prep — DevOps & Cloud

How to Approach DevOps Interviews

DevOps interviews test three things: conceptual understanding (can you explain it simply?), practical knowledge (have you actually done it?), and problem-solving (can you debug a broken pipeline?). Always answer with real examples — even if they're from personal projects.

🐧 Linux Interview Questions

Q: What is the difference between a process and a daemon?

A process is any running program — it has a PID, uses CPU and memory, and exits when done. A daemon is a background process that runs continuously without user interaction, usually started at boot. Examples: nginx (web server daemon), sshd (SSH daemon). Daemons typically end in 'd' by convention.

Q: What does chmod 755 mean?

chmod 755 script.sh sets permissions using the octal system: 7 (owner) = read+write+execute (4+2+1), 5 (group) = read+execute (4+1), 5 (others) = read+execute. So the owner can do everything, group and others can read and run but not modify. Always use 755 for scripts you want to be executable.

Q: What is the difference between > and >> in shell?

> redirects output and overwrites the file — use it carefully, it deletes the existing content. >> redirects output and appends to the file, preserving existing content. Example: echo "line1" > file.txt creates/overwrites; echo "line2" >> file.txt adds to the file.

🌿 Git Interview Questions

Q: What is the difference between git merge and git rebase?

git merge creates a new "merge commit" that combines two branches — it preserves the full history of both branches. git rebase rewrites the history by replaying your commits on top of another branch — it creates a cleaner, linear history but rewrites commit hashes. Rule: use merge for public/shared branches, rebase for local cleanup before pushing.

Q: What is git stash?

git stash temporarily saves your uncommitted changes (both staged and unstaged) so you can switch branches or work on something else without committing half-done work. Run git stash pop to restore your saved changes later. Think of it as a clipboard for your work-in-progress.

Q: What is the difference between git fetch and git pull?

git fetch downloads changes from the remote repository but does NOT merge them into your local branch — it just updates your local copy of the remote branches. git pull = git fetch + git merge — it downloads AND merges. Use fetch when you want to see what changed before merging.

🐳 Docker Interview Questions

Q: What is the difference between a Docker image and a container?

A Docker image is a read-only template — like a recipe or a blueprint. It contains the OS, dependencies, and your application code. A container is a running instance of an image — like a dish cooked from the recipe. You can run many containers from the same image simultaneously. Images are stored in registries (Docker Hub); containers run on your host.

Q: What is the difference between Docker and a VM?

A VM virtualizes an entire computer including its own OS — heavy, slow to start (minutes), uses gigabytes of RAM. Docker containers share the host OS kernel — lightweight, start in seconds, use megabytes. The trade-off: VMs provide stronger isolation (each has its own kernel); containers are faster and more efficient but share the kernel.

☸️ Kubernetes Interview Questions

Q: What is the difference between a Pod and a Deployment?

A Pod is the smallest deployable unit in Kubernetes — it wraps one or more containers that share the same network and storage. If a Pod dies, it's gone. A Deployment is a controller that manages a desired number of identical Pod replicas. If a Pod crashes, the Deployment automatically recreates it. In practice, you almost never create bare Pods — always use a Deployment so your app self-heals.

Q: What is the difference between ClusterIP, NodePort, and LoadBalancer services?

ClusterIP (default) exposes the service on an internal IP — only reachable from within the cluster. NodePort opens a port on every node (30000–32767 range) so external traffic can reach the service via NodeIP:NodePort — useful for dev/testing. LoadBalancer provisions a cloud load balancer (e.g. AWS ELB) in front of the nodes — the right choice for production internet-facing services. In Minikube, use minikube service <name> to access a LoadBalancer service locally.

Q: What happens when you run kubectl apply -f deployment.yaml?

kubectl sends the manifest to the API Server, which validates it and persists it to etcd. The Controller Manager (specifically the Deployment controller) detects the desired state differs from current state and creates a ReplicaSet. The Scheduler assigns each Pod to a suitable node. The kubelet on that node pulls the image and starts the container. The control loop then continuously reconciles — if a Pod dies, the whole sequence repeats automatically.

Q: What is a ConfigMap and when would you use a Secret instead?

A ConfigMap stores non-sensitive configuration as key-value pairs — environment names, feature flags, config file contents. A Secret stores sensitive data (passwords, tokens, TLS certs) and is base64-encoded (not encrypted by default, but can be encrypted at rest with KMS). Rule: if a value would be a problem if someone saw it in a log or screenshot → use a Secret. Both can be mounted as environment variables or as files inside containers.

Q: Your Pod is stuck in CrashLoopBackOff — how do you debug it?

Step-by-step: (1) kubectl get pods — confirm the status and how many restarts. (2) kubectl describe pod <name> — check Events at the bottom for OOMKilled, image pull errors, or failed liveness probes. (3) kubectl logs <name> --previous — see logs from the crashed container. (4) If the container exits immediately, temporarily override the command with command: ["sleep", "3600"] to keep it alive and exec in to debug. Common causes: app crash on startup, wrong env var, missing ConfigMap/Secret, or insufficient memory.

Q: What is the difference between a liveness probe and a readiness probe?

A liveness probe answers: "Is this container still alive?" — if it fails, Kubernetes restarts the container. Use it to detect deadlocks or hung processes. A readiness probe answers: "Is this container ready to serve traffic?" — if it fails, Kubernetes removes the Pod from the Service's endpoints (no traffic sent) but does NOT restart it. Use readiness probes during startup or when your app temporarily can't handle requests (e.g. loading a large config). A Pod can be alive but not ready.

🏗️ Terraform Interview Questions

Q: What is the difference between terraform plan and terraform apply?

terraform plan is a dry run — it compares your configuration against the current state file and shows exactly what will be created, changed, or destroyed. Nothing is modified. terraform apply actually executes those changes against your infrastructure. Best practice: always run plan first, review the output carefully, and only apply when you're sure. In CI/CD, save the plan as an artifact (-out=plan.tfplan) so apply uses the exact same plan that was reviewed.

Q: What is the Terraform state file and why is it critical?

The state file (terraform.tfstate) is Terraform's source of truth — it maps your configuration to real infrastructure resources. Without it, Terraform doesn't know what it already created, and would try to recreate everything. In teams, always use remote state (S3 + DynamoDB for locking, or Terraform Cloud) — never commit the state file to Git since it can contain secrets. If the state gets out of sync with reality, use terraform import to bring existing resources under management, or terraform refresh to sync state to actual infrastructure.

Q: What is the difference between a Terraform resource and a data source?

A resource (resource "aws_instance" "web") creates and manages infrastructure — Terraform owns its lifecycle. A data source (data "aws_ami" "ubuntu") reads existing infrastructure that Terraform didn't create — it's read-only. Use data sources to look up AMI IDs, existing VPCs, or shared secrets from SSM Parameter Store without hardcoding values or creating duplicates.

Q: What are Terraform modules and why use them?

A module is a reusable package of Terraform configuration — a folder of .tf files with defined inputs (variables) and outputs. Instead of copy-pasting a VPC setup for every environment, you write it once as a module and call it with different variable values for dev, staging, and prod. This enforces consistency, reduces duplication, and makes large codebases manageable. The public Terraform Registry has community modules for most AWS services — evaluate before writing your own.

Q: How would you manage secrets in Terraform without committing them to Git?

Several approaches: (1) Environment variables — Terraform auto-reads TF_VAR_<name> env vars, so secrets stay out of files. (2) AWS SSM Parameter Store or Secrets Manager — use a data source to fetch secrets at plan/apply time. (3) Vault — HashiCorp Vault provider can inject secrets dynamically. Never use default values in variable blocks for secrets, never put secrets in terraform.tfvars if it's committed, and add *.tfvars to .gitignore.
