Module 08.5 — CI/CD

GitHub Actions — Modern CI/CD

Jenkins vs GitHub Actions — Why the Shift?

Jenkins has been the CI/CD standard for years — but it requires you to manage a server, install plugins, and maintain infrastructure. GitHub Actions is built directly into GitHub. No server to manage, no plugins to install, no separate UI to learn. Push code → pipeline runs. That's it.

Aspect🤖 Jenkins⚡ GitHub Actions
SetupInstall on a server, configure pluginsZero setup — just add a .yml file
InfrastructureYou manage the serverGitHub manages runners for you
CostServer costs + maintenance timeFree for public repos, 2000 min/month free for private
ConfigJenkinsfile (Groovy)YAML in .github/workflows/
Marketplace1000+ plugins20,000+ community actions
IntegrationGitHub webhook neededNative GitHub integration
Learning curveSteepModerate — YAML based
💡 Real World

Most startups and modern tech companies use GitHub Actions. Jenkins is still common in large enterprises with legacy setups. As a DevOps engineer you need to know both — but GitHub Actions is becoming the default for new projects.

Core Concepts

📋
Workflow
A YAML file in .github/workflows/. Defines the entire automation — when it runs, what jobs it contains, and what each job does.
⚡
Event (Trigger)
What starts the workflow — a push, a PR, a schedule, a manual trigger, or an external event. One workflow can have multiple triggers.
💼
Job
A set of steps that run on the same runner. Jobs run in parallel by default. Use needs: to run them sequentially.
🔢
Step
A single task inside a job — either a shell command (run:) or a community action (uses:). Steps run sequentially within a job.
🖥️
Runner
The virtual machine that executes jobs. GitHub provides Ubuntu, Windows, and macOS runners for free. You can also host your own runner.
🧩
Action
A reusable unit of code from the GitHub Marketplace. actions/checkout, actions/setup-node, docker/build-push-action — use these instead of writing everything from scratch.

Anatomy of a Workflow File

.github/workflows/ci.yml
# Workflow name — shows in GitHub Actions tab name: CI Pipeline # ── Triggers ───────────────────────────────────── on: push: branches: [main, develop] # run on push to these branches pull_request: branches: [main] # run on PRs targeting main workflow_dispatch: # allow manual trigger from GitHub UI # ── Jobs ───────────────────────────────────────── jobs: build: name: Build & Test runs-on: ubuntu-latest # runner OS steps: # Step 1 — Checkout your code - name: Checkout code uses: actions/checkout@v4 # community action # Step 2 — Set up Node.js - name: Setup Node.js uses: actions/setup-node@v4 with: node-version: '20' # Step 3 — Install dependencies - name: Install dependencies run: npm ci # shell command # Step 4 — Run tests - name: Run tests run: npm test # Step 5 — Build - name: Build run: npm run build

Triggers — When Does the Workflow Run?

YAML — All common trigger types
on: # Push to specific branches or tags push: branches: [main, 'release/*'] tags: ['v*'] # triggers on v1.0, v2.3 etc paths: - 'src/**' # only if files in src/ changed # Pull request events pull_request: branches: [main] types: [opened, synchronize, reopened] # Scheduled — cron syntax schedule: - cron: '0 2 * * *' # every day at 2am UTC # Manual trigger — button in GitHub UI workflow_dispatch: inputs: environment: description: 'Deploy to' required: true default: 'staging' type: choice options: [staging, production] # Triggered by another workflow workflow_call:

Real Workflows — Copy & Use

Node.js CI — Test, Build, Coverage

.github/workflows/node-ci.yml
name: Node.js CI on: push: branches: [main] pull_request: branches: [main] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: '20' cache: 'npm' # cache node_modules automatically - run: npm ci - run: npm test -- --coverage - name: Upload coverage uses: codecov/codecov-action@v4

Java / Maven CI

.github/workflows/maven-ci.yml
name: Java CI on: push: branches: [main] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Set up JDK 17 uses: actions/setup-java@v4 with: java-version: '17' distribution: 'temurin' cache: 'maven' - name: Build with Maven run: mvn clean package -DskipTests - name: Run tests run: mvn test - name: Upload JAR artifact uses: actions/upload-artifact@v4 with: name: app-jar path: target/*.jar

Docker Build, Scan & Push to Docker Hub

.github/workflows/docker.yml
name: Docker Build & Push on: push: tags: ['v*'] # only on version tags jobs: docker: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 # Login to Docker Hub using secrets - name: Login to Docker Hub uses: docker/login-action@v3 with: username: ${{ secrets.DOCKERHUB_USERNAME }} password: ${{ secrets.DOCKERHUB_TOKEN }} # Build and push with cache - name: Build & push uses: docker/build-push-action@v5 with: context: . push: true tags: ${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.ref_name }} cache-from: type=gha cache-to: type=gha,mode=max # Scan image for vulnerabilities - name: Scan with Trivy uses: aquasecurity/trivy-action@master with: image-ref: ${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.ref_name }} severity: 'HIGH,CRITICAL' exit-code: '1' # fail if vulnerabilities found

Secrets & Environment Variables

Never hardcode passwords or API keys in your workflow files. GitHub has a built-in secrets manager — go to Repository → Settings → Secrets and variables → Actions to add them.

YAML — Using secrets and env vars
jobs: deploy: runs-on: ubuntu-latest # Environment-level variables (non-sensitive) env: NODE_ENV: production APP_PORT: '3000' steps: - uses: actions/checkout@v4 # Use secrets with ${{ secrets.SECRET_NAME }} - name: Configure AWS credentials uses: aws-actions/configure-aws-credentials@v4 with: aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }} aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }} aws-region: ap-south-1 # Secrets are masked in logs — never printed even with echo - name: Deploy run: | echo "Deploying to $NODE_ENV" aws s3 sync ./dist s3://my-bucket
⚠️ GitHub Context Variables

GitHub automatically provides useful variables: ${{ github.sha }} (commit hash), ${{ github.ref_name }} (branch/tag name), ${{ github.actor }} (who triggered), ${{ github.repository }} (repo name). Use these instead of hardcoding values.

Matrix Builds — Test Across Multiple Versions

Matrix strategy runs the same job multiple times with different configurations simultaneously. Perfect for testing across Node versions, OS types, or environments.

YAML — Matrix build
jobs: test: runs-on: ${{ matrix.os }} strategy: matrix: os: [ubuntu-latest, windows-latest, macos-latest] node: [18, 20, 22] fail-fast: false # don't cancel all if one fails steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: ${{ matrix.node }} - run: npm ci && npm test # This creates 9 parallel jobs: # ubuntu + node 18 | ubuntu + node 20 | ubuntu + node 22 # windows + node 18 | windows + node 20 | windows + node 22 # macos + node 18 | macos + node 20 | macos + node 22

Job Dependencies & Full CI/CD Pipeline

Jobs run in parallel by default. Use needs: to create a dependency chain — this is how you build a full CI/CD pipeline.

.github/workflows/full-pipeline.yml
name: Full CI/CD Pipeline on: push: branches: [main] jobs: # Job 1 — Run tests test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: '20', cache: 'npm' } - run: npm ci && npm test # Job 2 — Build Docker image (only if tests pass) build: needs: test # waits for test job runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: docker/login-action@v3 with: username: ${{ secrets.DOCKERHUB_USERNAME }} password: ${{ secrets.DOCKERHUB_TOKEN }} - uses: docker/build-push-action@v5 with: push: true tags: myapp:${{ github.sha }} # Job 3 — Deploy to staging (only if build passes) deploy-staging: needs: build runs-on: ubuntu-latest environment: staging # uses environment-level secrets steps: - uses: actions/checkout@v4 - name: Deploy to K8s run: | kubectl set image deployment/my-app \ my-app=myapp:${{ github.sha }} # Job 4 — Deploy to production (manual approval required) deploy-production: needs: deploy-staging runs-on: ubuntu-latest environment: production # GitHub will pause and wait for approval steps: - name: Deploy to production run: echo "Deploying to production..."
💡 Environment Protection Rules

Go to Settings → Environments → production → Required reviewers to add approvers. GitHub will pause the workflow and send a notification before running the production deployment — no code goes to prod without a human sign-off.

Caching — Speed Up Your Workflows

Without caching, every run downloads all dependencies from scratch. With caching, unchanged dependencies are restored from cache — cutting build times from minutes to seconds.

YAML — Manual cache with actions/cache
steps: - uses: actions/checkout@v4 # Cache node_modules - name: Cache node modules uses: actions/cache@v4 with: path: ~/.npm key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }} restore-keys: | ${{ runner.os }}-node- # Cache Maven dependencies - name: Cache Maven packages uses: actions/cache@v4 with: path: ~/.m2 key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }} # Key tip: hashFiles() generates a unique key from your lockfile # Cache is invalidated only when lockfile changes — perfect!

Reusable Workflows — DRY Pipelines

If you have 10 microservices each with their own workflow, you don't want to copy-paste the same pipeline 10 times. Reusable workflows let you define a workflow once and call it from any other workflow.

.github/workflows/reusable-deploy.yml — Define once
name: Reusable Deploy on: workflow_call: # makes this workflow reusable inputs: environment: required: true type: string image-tag: required: true type: string secrets: KUBE_CONFIG: required: true jobs: deploy: runs-on: ubuntu-latest steps: - name: Deploy to ${{ inputs.environment }} run: | echo ${{ secrets.KUBE_CONFIG }} | base64 -d > kubeconfig kubectl set image deployment/app app=${{ inputs.image-tag }}
.github/workflows/main-pipeline.yml — Call it
jobs: deploy: uses: ./.github/workflows/reusable-deploy.yml with: environment: production image-tag: myapp:${{ github.sha }} secrets: KUBE_CONFIG: ${{ secrets.KUBE_CONFIG }}

Practical Tips

⚡
Always pin action versions
Use actions/checkout@v4 not @main. Unpinned actions can break your pipeline when the action author pushes changes.
🔒
Limit permissions
Add permissions: read-all at the top and only grant what each job needs. This follows least-privilege — a compromised action can't push code or delete branches.
💾
Use cache for everything
Cache npm, Maven, pip, Docker layers. The difference between a 30-second build and a 5-minute build is usually caching.
🏃
Self-hosted runners
For private repos with heavy usage, set up your own runner on EC2. Free minutes run out fast. Self-hosted runners also let you access private VPC resources.
🧪
act — test locally
act is a CLI tool that runs GitHub Actions workflows locally using Docker. Essential for debugging — no need to push and wait to see if your YAML works.
📋
Path filters
Use paths: in triggers so workflows only run when relevant files change. Frontend workflow shouldn't run when you only changed backend code.
Terminal — Test workflows locally with act
# Install act brew install act # Mac curl https://raw.githubusercontent.com/nektos/act/master/install.sh | sudo bash # Run all workflows locally act # Run a specific event act push act pull_request # Run a specific job act -j build # Pass secrets act -s DOCKERHUB_TOKEN=mytoken
🚀 Mini Project — Full CI/CD with GitHub Actions

Build a complete pipeline for your DevOps Buddy or any project:

  1. Create .github/workflows/ci.yml — on every push to main: checkout → install → test → build
  2. Add a Docker job that builds and pushes to Docker Hub using secrets — only on version tags
  3. Add a matrix build that tests on Node 18, 20, and 22 simultaneously
  4. Set up a production environment with a required reviewer — so deploys need approval
  5. Add caching for node_modules using actions/cache — compare build times before and after
  6. Install act and run your workflow locally without pushing to GitHub
✅ Module Summary
  • GitHub Actions is CI/CD built into GitHub — no server to manage, just YAML files
  • Workflows live in .github/workflows/ and trigger on events (push, PR, schedule, manual)
  • Jobs run in parallel by default — use needs: for sequential pipelines
  • Use secrets. for credentials — never hardcode passwords in workflow files
  • Matrix builds run the same job across multiple OS/versions simultaneously
  • Cache dependencies with actions/cache — biggest single performance improvement
  • Reusable workflows prevent copy-pasting pipelines across microservices
  • Use environment protection rules for production — always require human approval
  • Pin action versions and limit permissions — security basics for every workflow
  • Test locally with act before pushing
