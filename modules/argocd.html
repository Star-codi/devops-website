ArgoCD — GitOps Continuous Delivery for Kubernetes

What is GitOps?

GitOps is a way of operating Kubernetes where your Git repository is the single source of truth for everything — infrastructure, application configs, Kubernetes manifests. If it's not in Git, it doesn't exist in your cluster.

🏦 Analogy — Git as your bank ledger

Think of your Git repo as a bank ledger. Every transaction (deployment change) is recorded. The current balance (cluster state) is derived from all past transactions. If something's wrong, you audit the ledger — not the vault. ArgoCD is the accountant that continuously checks the ledger matches the vault.

📖
Declarative
You describe the desired state in YAML. ArgoCD figures out how to get there — you never imperatively run kubectl apply in production.
🔄
Versioned
Every change is a Git commit. Roll back a bad deploy with git revert. Full audit trail of who changed what and when.
🤖
Automated
ArgoCD watches your repo and automatically syncs changes to the cluster. No manual steps, no SSH into servers.
✅
Self-Healing
If someone manually changes something in the cluster, ArgoCD detects the drift and can auto-correct it back to Git state.

Installing ArgoCD

bash
# Create namespace kubectl create namespace argocd # Install ArgoCD kubectl apply -n argocd -f \ https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml # Wait for pods to be ready kubectl wait --for=condition=Ready pods --all -n argocd --timeout=300s # Get initial admin password kubectl -n argocd get secret argocd-initial-admin-secret \ -o jsonpath="{.data.password}" | base64 -d # Access UI (port-forward) kubectl port-forward svc/argocd-server -n argocd 8080:443 # Open: https://localhost:8080 (admin / <password above>)

Core Concept — The Application CRD

Everything in ArgoCD revolves around the Application Custom Resource. It defines: where the source YAML lives (Git), and where to deploy it (Kubernetes cluster + namespace).

application.yaml
apiVersion: argoproj.io/v1alpha1 kind: Application metadata: name: my-app namespace: argocd spec: project: default # WHERE to pull configs from source: repoURL: https://github.com/your-org/k8s-configs.git targetRevision: main # branch/tag/commit path: apps/my-app # folder inside the repo # WHERE to deploy destination: server: https://kubernetes.default.svc # in-cluster namespace: production syncPolicy: automated: prune: true # delete resources removed from Git selfHeal: true # auto-fix manual cluster changes syncOptions: - CreateNamespace=true

App of Apps Pattern

A common pattern for managing many applications — one root Application points to a folder of other Application manifests. ArgoCD bootstraps your entire platform from a single git push.

root-app (ArgoCD Application) │ ├── apps/ │ ├── frontend-app.yaml → deploys frontend │ ├── backend-app.yaml → deploys backend │ ├── database-app.yaml → deploys database │ └── monitoring-app.yaml → deploys Prometheus stack │ ArgoCD watches this folder and creates each Application automatically
💡 When to use App of Apps

Use this pattern when you have more than 3-4 applications. It lets you manage your entire cluster state declaratively — one kubectl apply to bootstrap everything, forever.

ArgoCD CLI Cheat Sheet

bash
# Login argocd login localhost:8080 --username admin --password <pass> # List all apps argocd app list # Get app status argocd app get my-app # Manually trigger sync argocd app sync my-app # Rollback to previous version argocd app rollback my-app 1 # 1 = history ID # View app history argocd app history my-app # Delete app (keeps cluster resources) argocd app delete my-app --cascade=false

Jenkins vs ArgoCD — Key Difference

🤖
Jenkins (Push CD)
Jenkins runs a pipeline, builds the image, then pushes (kubectl apply) to the cluster. Jenkins needs cluster credentials. If Jenkins is down, no deployments.
🔁
ArgoCD (Pull CD)
ArgoCD sits inside the cluster and pulls desired state from Git. Cluster credentials never leave. Works even when CI is down. Scales to many clusters easily.
🏆 Best Practice — Use both together

Jenkins/GitHub Actions handles CI: test → build image → push to registry → update the image tag in Git. ArgoCD handles CD: detects the Git change → syncs to cluster. Clean separation of concerns.

Sync Status & Health

ArgoCD tracks two things independently for every application:

🔄
Sync Status
Synced — cluster matches Git.
OutOfSync — Git has changes not yet applied.
Unknown — can't determine state.
❤️
Health Status
Healthy — all pods running, no errors.
Progressing — deployment in progress.
Degraded — pods crashing or failing.
Missing — resource doesn't exist yet.
